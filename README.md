# Миграция рабочих мест на Astra Linux: организация сопровождения

**Кейс системного аналитика в подразделении сопровождения рабочих мест банка.**

Задача — организовать учёт работ и взаимодействие подразделений при переходе с Windows на Astra Linux. Аналитик контролирует исполнение, помогает разбирать инциденты и связывает участников процесса, но не руководит кураторами площадок и не определяет архитектуру миграции.

Материалы подготовлены по описанным условиям задачи. Банк и площадки обезличены. Это описание предлагаемого порядка работы, а не внутренний регламент банка и не подтверждение фактически выполненной миграции. Все номера обращений, рабочие места, сроки и результаты в примерах вымышлены.

## Суть решения

У каждого рабочего места независимо учитываются:

1. **Фактическая конфигурация:** Windows, Astra Linux вместе с Windows, только Astra Linux или состояние не подтверждено.
2. **Работы:** удалённая установка, ручная установка, ожидание решения, последующий вывод Windows.
3. **Нарушения работы:** отдельные инциденты с собственными исполнителями и сроками.

Установка Astra Linux считается завершением миграции по условиям задачи, в том числе при **dualboot — двойной загрузке, когда на компьютере сохранены обе операционные системы**. При этом остаётся отдельная задача на вывод Windows. Она выполняется после применимой команды группы сопровождения программного обеспечения.

Закрытие установки не закрывает инциденты и задачу вывода Windows. Отправленное задание установки не считается подтверждённым результатом.

## Готовые рабочие формы

[Карточка АРМ](шаблоны/01-карточка-арм.md) · [Передача ручных работ](шаблоны/02-передача-работ.md) · [Вывод Windows](шаблоны/03-вывод-windows.md) · [Инцидент](шаблоны/04-инцидент.md) · [Сводка начальнику](шаблоны/05-сводка.md) · [Запрос решения](шаблоны/06-запрос-решения.md).

**АРМ — автоматизированное рабочее место:** единица учёта, на которой выполняется миграция. Для удалённой работы важно не перепутать её с устройством, с которого подключается пользователь.

Формы показывают состав сведений. Их предполагается размещать в существующих записях Service Desk, а не вести отдельные несвязанные журналы.

## Проверяемый пример

В [демонстрационных данных](примеры/02-данные.json) описана волна из 12 вымышленных АРМ: четыре с одной Astra, три с двойной загрузкой, четыре с Windows и одно с неподтверждённым состоянием. Есть возврат к Windows, незавершённая ручная установка, частичная готовность приложений и открытый инцидент после успешной установки.

[Сводка](примеры/03-сводка.md) рассчитана по этим данным. Это не показатели банка.

Для локальной проверки требуется Python версии 3.10 или новее. Из корневой папки репозитория:

```bash
python проверки/проверить.py
```

Проверка не подключается к банку, не выполняет миграцию и не изменяет данные. Она сверяет ссылки между документами, состав примера, условия завершения задач и расчёт показателей. Это проверка логики кейса, а не испытания Astra Linux.

## Что намеренно не включено

Нет инструкций по установке или удалению операционных систем, настроек защиты, перечней банковского программного обеспечения, адресов инфраструктуры, персональных данных и выгрузок из Service Desk. Совместимость и техническую готовность подтверждают профильные подразделения, а не автор этого описания.
