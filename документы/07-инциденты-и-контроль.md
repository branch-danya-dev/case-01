# 07. Инциденты, передача обращений и контроль исполнения

[К содержанию](../README.md) · [Далее: показатели](08-показатели.md)

## Сначала определить тип ситуации

| Ситуация | Как её учитывать |
|---|---|
| Удалённая установка не выполнена, сотрудник продолжает работать без нарушения функций | Незавершённая работа с причиной и следующим действием; инцидент не создаётся автоматически только ради учёта неудачной установки |
| После работ пользователь не может войти, подключиться к АРМ или выполнить нужную функцию | Инцидент по действующим правилам, связанный с работой миграции |
| Windows заранее сохранена ради ещё не готового ПО, нужная функция доступна предусмотренным способом | Задача полного перехода с зависимостью; само наличие Windows не объявляется инцидентом |
| Аналогичные нарушения повторяются на разных АРМ | Связать обращения с общей причиной или отдельной записью проблемы, если такой процесс предусмотрен |

Окончательная классификация выполняется по действующему процессу Service Desk. Совпадение сбоя по времени с миграцией — повод для проверки, а не доказательство её причинности.

## Минимальная запись для передачи

Нужны затронутый АРМ или группа АРМ, нарушенная функция, время обнаружения, влияние на работу, результаты доступной первичной проверки, текущая конфигурация, связанная работа миграции и ожидаемое действие профильной группы.

Пароли, ключи, содержимое пользовательских документов и закрытые журналы не копируются в общедоступное описание. Используется разрешённая ссылка с учётом прав получателя.

## Работа аналитика по открытому обращению

Аналитик проверяет назначение, а не только наличие комментария «передали». Выясняет, кто выполняет следующее действие, какой результат ожидается и когда нужно повторно проверить состояние.

При отсутствии ответа он уточняет положение дел у назначенной группы. Если требуется сменить приоритеты, привлечь ресурс другой площадки или разрешить спор ответственности, готовит обращение начальнику с фактами и вариантами решения. Руководство инженерами через кураторов сохраняется.

В критической ситуации применяется действующий срочный маршрут эскалации. **Эскалация** — передача вопроса участнику, у которого есть нужные полномочия или компетенция. Это не обязательно смена исполнителя инцидента.

## Сроки не выдумываются

**SLA — Service Level Agreement**, соглашение об уровне обслуживания: принятые обязательства по срокам и качеству сервиса. **OLA — Operational Level Agreement**, соглашение о взаимодействии внутренних подразделений. Их точные значения для банка не заданы.

Контрольный срок следующего уточнения не подменяет SLA или OLA. Смена группы, ожидание ПО и отправка запроса сами по себе не дают оснований обнулить или приостановить срок инцидента. Используются правила действующей системы.

Приоритет определяется влиянием и срочностью по принятой шкале. Статус VIP и принадлежность закрытой площадке учитываются в организации работ, но не заменяют эти критерии автоматически.

## Когда группы не согласны с принадлежностью проблемы

Аналитик фиксирует выполненные проверки и конкретный нерешённый вопрос: например, требуется ли изменить настройку АРМ или исправить приложение. Организует обмен сведениями профильных групп. При необходимости выносит начальнику запрос на совместную диагностику или назначение ответственного.

Переадресация без новых сведений не считается прогрессом. В сводке видны длительность ожидания, текущая группа и требуемое решение. Аналитик не объявляет виновной одну из групп без подтверждения причины.

## Завершение инцидента

Подтверждение восстановления оформляется по действующему процессу: результатом исполнителя, разрешённой проверкой и, когда это предусмотрено, подтверждением пользователя. Аналитик контролирует наличие этого основания, но не вводит новый обязательный порядок приёмки вместо существующего.

Успешная установка Astra не закрывает инцидент автоматически. И наоборот: восстановление работы через Windows может завершить инцидент, оставив открытой задачу повторной установки или вывода Windows.

## Повторяющиеся нарушения

Для общей причины собирается связная картина: какие АРМ затронуты, какая функция нарушена, что общего в условиях, какое решение предложено профильной группой. Согласованное решение передаётся участникам следующих волн разрешённым способом.

Это не самостоятельный технический пилот аналитика. Он описывает проблему и обеспечивает связь результатов с работами сопровождения.
