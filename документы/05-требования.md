# 05. Требования к учёту и взаимодействию

[К содержанию](../README.md) · [Далее: двойная загрузка](06-двойная-загрузка.md)

Это предлагаемые требования для согласования с начальником и владельцами процессов. Они не объявляют действующие регламенты изменёнными. Под «система должна позволять» понимается использование имеющихся возможностей Service Desk; при их отсутствии требуется отдельное согласование изменения.

**Требование** описывает нужное правило или возможность. **Условие проверки** показывает, как отличить выполненное требование от невыполненного.

## Функциональные требования

Функциональные требования определяют, что необходимо учитывать и контролировать.

| Код | Требование | Условие проверки |
|---|---|---|
| ТР-01 | АРМ однозначно определяется по устойчивому идентификатору, а участие — по паре «волна + АРМ» | Повторная строка или попытка не увеличивает число АРМ |
| ТР-02 | Для волны сохраняются источник, версия состава и основания изменений | Перенос АРМ не исчезает из истории и не меняет старую сводку без обозначения новой версии |
| ТР-03 | Конфигурация, выполнение установки и инциденты учитываются независимо | Закрытая установка может сосуществовать с двойной загрузкой и открытым инцидентом |
| ТР-04 | Отправка задания не подтверждает установку | При отсутствии результата запись остаётся незавершённой; неизвестная конфигурация не превращается в Windows по умолчанию |
| ТР-05 | Установка подтверждается источником, временем и результатом; принятие пользователем не добавляется как новый критерий миграции | Подтверждённая Astra учитывается как установленная даже при открытом инциденте |
| ТР-06 | Передача ручных работ сохраняет связь с удалённой попыткой и содержит следующий шаг | Инженер видит АРМ, основание передачи, результат попытки и назначенную работу |
| ТР-07 | Каждое ожидание имеет причину, ответственного за следующее действие и дату контроля | Нельзя оставить запись только со словом «ждём» |
| ТР-08 | Для каждого АРМ с двойной загрузкой сохраняется отдельная незавершённая задача вывода Windows | Закрытие установки не закрывает эту задачу |
| ТР-09 | Один АРМ может иметь несколько независимых причин сохранения Windows | Готовность одного из двух приложений не снимает вторую зависимость |
| ТР-10 | Основание вывода Windows связано с применимой командой сопровождения ПО | Команда для другой группы пользователей или другой версии ПО не считается достаточным основанием |
| ТР-11 | Завершение вывода Windows подтверждается фактическим результатом, а не выдачей команды | При запланированных работах Windows продолжает учитываться |
| ТР-12 | После возврата к Windows сохраняются история установки и связанные повторные работы | Историческое количество установок не подменяет текущую конфигурацию |
| ТР-13 | Инцидент связан с затронутыми АРМ и при необходимости с работами миграции | Один общий инцидент не размножается для получения отдельной записи на каждый АРМ |
| ТР-14 | Передача обращения не считается восстановлением сервиса | Видны текущая назначенная группа, следующее действие и подтверждение восстановления при завершении |
| ТР-15 | Сводка имеет момент среза, версию списка и воспроизводимые правила расчёта | По тем же данным получается тот же результат |
| ТР-16 | Отдельно видны установка Astra, сохранённый Windows и нарушения работы | Нельзя заменить три показателя одним процентом «готовности» |
| ТР-17 | Поручения кураторам по ресурсам и приоритетам проходят через начальника | Аналитик готовит запрос решения, но не меняет распределение сотрудников самостоятельно |
| ТР-18 | Неопределённость и противоречие данных видимы | Неизвестная причина сохранения Windows требует уточнения, но факт уже установленной Astra не скрывается |

## Требования к качеству работы

| Код | Требование | Как проверять |
|---|---|---|
| НТ-01 | Используются разрешённые каналы и разграничение доступа | Проверить состав сведений общей сводки и права получателей; закрытые материалы не копировать в общий реестр |
| НТ-02 | Сохраняется история изменений состояния, назначения и оснований | По записи можно восстановить, кто и на каком основании изменил сведения |
| НТ-03 | Сроки инцидентов считаются по действующим правилам Service Desk | Передача группы или запись «ожидание» сами по себе не сбрасывают и не приостанавливают срок |
| НТ-04 | Контроль масштабируется до согласованного объёма, потенциально 10 000 АРМ | На разрешённых тестовых данных проверить штатные выборки и отчёты; допустимое время согласовать с владельцем системы, не назначать произвольно |
| НТ-05 | Общий учёт не заменяется несвязанными таблицами площадок | Сводка содержит ссылки на первичные записи; временная разрешённая выгрузка имеет дату и не становится самостоятельным источником состояний |

## Как применять без незапланированной доработки Service Desk

Для каждого требования выясняется, обеспечивается ли оно существующими полями, связями и представлениями. Например, задача вывода Windows может быть обычной связанной задачей, а зависимости — структурированными строками её описания.

Если необходимой возможности нет, аналитик фиксирует разрыв и предлагает владельцу системы вариант настройки. До решения допустим согласованный ручной контроль внутри имеющегося процесса. Кейс не предполагает самостоятельной разработки нового приложения, интеграции или прямого изменения базы данных.
